# CHANGELOG — bugfix

## 19.10.2026

- **Навык создан** по стоящей процедуре пользователя: свежий baseline-анализ → починка →
  повторный анализ → сравнение двух списков → коммит только когда новых багов нет →
  проверка чистой установки. Первый применённый раунд — `brain-hack-analyze`
  (baseline 5: 1 мажорный, 4 минорных → после: 0, новых 0 → коммит; чистая установка).
- **Два класса багов, которые ловит только прогон чистой установки** (записаны в навык после
  раунда на brain-hack-analyze, harness 18/18 после починки):
  - чтение на импорте артефактов, создаваемых установщиком: файлы `model_setup.py` не в репо,
    и модуль, который читает их на импорте, падает на свежем клоне — навык не деградировал к
    лексикону, а ломался целиком; тесты логики обязаны подменять каталог и обходить проверку
    доступности, а модуль — отвечать честный `unavailable`;
  - загрязнение глобального `sys.path` плагином: поздний импорт в том же процессе берёт модуль
    из домашней папки автора, а не из копии. Тест проходил отдельно и падал в полном прогоне —
    порядкозависимое падение является доказательством общего изменяемого состояния, а не
    сломанного теста.
- Проверка навыка: `py_compile` не считается проверкой — после правки скрипта обязана быть
  одна read-only живая проверка; закреплённые числа тестов не являются фактом, писать
  фактическое число падающих по прогону.

### Дополнение по ходу раундов 20–22 (brain-hack-analyze)

- **Протокольный тест обязан читать баннер запуска процесса перед первым ответом на op и
  использовать фактические имена ключей протокола.** Прежний тест читал ответ на несуществующий
  op — это сдвигало все последующие ответы (тест читал не ту строку), а запрос с неверным именем
  ключа даёт пустой результат, который читается как «функция сломана» вместо «тест неверный».
  Пустой результат и отсутствие ответа — разные вещи; ветку unknown op надо тестировать отдельно.
  Доказательство: на тестовом кейсе с неверным ключом «как есть» даёт пустой результат, по правилу —
  ответ с именем op; на прогоне чистой установки это проявилось как падение теста, а не как баг навыка.
- **Порядок раунда: harness клонирует COMMITMITTED состояние, поэтому починки обязаны быть
  закоммичены до прогона.** Коммитный гейт выполняется сравнением списков, а баг, найденный прогоном
  чистой установки, починяется, перепроверяется и коммитится в том же раунде (сам harness — часть
  раунда и тоже коммитится). Сетевые шаги установочного пути проверяются как напечатанный план,
  а не как реальная установка, и harness обязан так же писать в отчёте.
  Доказательство: прогон на не закоммиченном состоянии клонирует прежнюю версию модуля и тест
  проходит, хотя починка ещё не попала в репо (замер: `git archive HEAD` даёт прежний
  `model_promote.py` без переноса меток, и новый тест на этой копии падает).
